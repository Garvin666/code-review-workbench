## 1. 试点目标与范围

验证「数据 → 模型 → 工作台」数据管道端到端可行，为后续把数据集真正接入工作台（真实代码 + 真实漏洞 + 真实审查意见）铺路。本轮只验证**管道**，不做 UI 改造、不做模型训练。

```
processed/unified/test.jsonl (12,497 条)
        │ sample.py  分层抽样(来源×语言, 剔除超长)
        ▼
samples.jsonl (12 条真实样本)
        │ backend.py golden|ollama|openai 三后端适配
        ▼

        │
        ▼
findings.jsonl + workbench_payload.json   ← 工作台 schema 存档
```

## 5. 解析层 —— 定级规则（extract.py）

- **漏洞样本**：按 `meta.cwe` 精确映射 —— 注入类(CWE-89/90/94/77/78) → **P0**；XSS/CSRF/上传/凭据/路径穿越/反序列化/XXE/SSRF 等 → **P1**。
- **批评/评论样本**：仅区分 改进意见(**P2**) 与 纯正面(**P3**)，不做关键词升级。
- 设计决策：**P0/P1 只产生于 CWE 确证漏洞**，与工作台"阻断级 = 工具确证缺陷"语义一致（避免 `inject`(依赖注入)、`credential`(配置路径) 等宽泛词在普通 review 中误升）。
- 人工真值/模型输出原文保留在 `reviews_raw.jsonl`，finding 内 `evidence` 字段留痕可追溯。

## 6. 试点结果

**严重度分布（14 条 findings / 12 样本）**

| 严重度 | 数量 | 构成 |
|---|---|---|
| P0 | 1 | CWE-89 SQL 注入（拼接用户输入进查询） |
| P1 | 3 | CWE-352 CSRF / CWE-434 上传 / CWE-798 硬编码凭据 |
| P2 | 8 | critique 改进意见 + GitHub PR 审查意见 |
| P3 | 2 | REVISED 修订建议 / 纯正面 |

**抽样亮点（来自真实语料）**

1. `cwe-na-02` **[CWE-89] SQL Injection (P0)**：`描述: 代码将用户输入直接拼入 SQL 查询…` — 可复现注入路径，符合工作台 P0 行内发现的表现形态。
2. `github-rust-02` `risingwave` 真实 PR 意见 (P2)：测试未验证 Java catalog 的 GCP credentials 路径生成正确 — 典型"测试覆盖缺口"类 review。
3. `dahoas-python-02` (P2)：`The code is repetitive and inefficient.` + REVISED 修订代码 (P3) — 三段式语料的 CRITIQUE/REVISED 拆分成功。

**耗时**：golden 模式 0.0s（无网络 IO）；真实模型后端耗时取决于所选模型。
